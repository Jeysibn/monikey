## 0. Final corrections (owner's conditional approval)

An independent Chromium review of the earlier mock reported four problems. Status after this round, each **re-tested** in `VERIFICATION.md`:

| # | Required correction | Result |
|---|---|---|
| 1 | Duplicate *Add transaction* buttons on mobile; the desktop-only action must stay hidden below 768px | **Fixed.** Cause: a later `.btn { display:inline-flex }` rule overrode the hide. Measured: 0 visible "Add transaction" buttons at 360 and 375 on every screen, exactly 1 at 768 and 1280, exactly one filled primary action per screen. |
| 2 | Add-account amount parser: zero values consistent, never `NaN` | **Fixed.** One parser (`parseMoney`) now serves every money field. Measured: `0`, `00`, `0.00`, `0.0`, `0.`, `000.00`, `0,000.00` are accepted as ₱0.00 for opening balance / owed-today; credit limit of 0, empty, negative, letters and 3 decimals are rejected with a clear message; the page never contains `NaN`. |
| 3 | Monthly summary amounts wrapping at 360/375 | **Fixed.** *This month* is now label-left / value-right rows (it was two columns, which wrapped "+₱36,500.00"). Measured: every amount is single-line and inside its card at 360, 375, 768 and 1280. |
| 4 | Self-host Manrope if ₱ and tabular figures work; keep a fallback | **Done.** Verified both; self-hosted in `docs/design/preview/fonts/` with the OFL licence; a sensible system-font fallback stack remains. |

The reviewer's screenshots were of the *earlier* mock; the visual layer was since rebuilt (flat deep-cobalt hero card, label/value rows, compact card tiles, soft-blue active navigation, bottom-sheet dialogs, Manrope). The four items above are about behavior and were re-measured on the new build.

## 4. Paper critique (no screenshots exist)

Taste Skill's seven app-screen questions, answered against the **design**, not a rendering:

1. **Is the screen's question answered by the biggest thing, read first?** Overview: yes — the hero net position (32px) leads, 1.33× the next figure (24px), and the sentence beneath states the finding. Activity: the list is the largest block. Accounts: two equal sections; the question ("have vs owe") is answered by their headings and subtotals.
2. **Do blocks share the screen's edges; any dead strips or stretched cards?** Designed to share edges. Known risk: the Overview desktop columns end at different heights with the default row counts (the wireframe shows the right column taller). Accounts columns are intentionally unstretched. **To verify in a browser.**
3. **Is colour only on data, status and the one primary action?** Yes by rule: cobalt on one button per screen and selected states; green on income; burnt orange on owed amounts; red only on errors/destructive. Face check (Manrope figures, equation strip, limit track) cannot be confirmed until rendered.
4. **Do numbers add up and line up?** Totals reconcile by script. Alignment (tabular figures, right edges) is specified, not yet seen. Every fact shown twice (e.g. ₱54,196.25 appears in the sentence and the "Money you have" figure) is meant to come from one variable.
5. **Zeros and missing values?** Specified: zero prints as `₱0.00`; missing is a muted `—`; empty sections keep their frame.
6. **Legend/colour clarity?** No charts and no legends. The limit track is labelled in words ("owed", "available") rather than by a key.
7. **Phone navigation folded and each block still answering its question?** Bottom bar replaces sidebar; each block stacks and keeps its heading and its main figure.

**Honest weak spots I would expect a reviewer to raise:** the equation strip adds a line some users may find redundant; the "Owed" chip repeats the information in the amount's colour and word; the Accounts desktop columns can look uneven.

## 5. Findings and concerns

### For the backend reviewer (Codex) — contract gaps the design touches
| # | Finding | Impact on the UI | Suggested resolution |
|---|---|---|---|
| B1 | `GET /api/credit-card-payments` has no `account_id` filter. | Activity's Account filter cannot be exact for payments. | **Codex-recommended:** add `account_id` to the payments endpoint (either side) and apply it **before** the limit. Client-side filtering of a capped list is not acceptable. |
| B2 | Transactions and payments are separate lists, each with its own `limit`. | "Latest 50" merged across two lists can omit entries; "Load more" is approximate. | **Codex-recommended:** request `limit + 1` from each filtered list, merge, sort, show `limit`. No combined endpoint needed. |
| B3 | No stable ordering key is exposed within the same date. | Same-day entries may reorder after edits. | **Codex-recommended:** expose `created_at` (both tables already have it) and order by date → `created_at` → source-and-ID tie-breaker. |
| B4 | `GET /api/accounts` example shows only card fields; the non-card balance field name is not specified. | Types guess `balance`. | Name it (e.g. `balance`) in the TLD; liquid balances and signed card debt are decimal strings that **may be negative**. Also decide whether `available_credit` is negative or clamped to 0 when over the limit (UI handles both, UI_UX_SPEC §6). |
| B5 | The summary is month-only (not account-filtered). | Activity shows an entry count but no totals when filtered. | Fine for v1; note as a deliberate limit. |
| B6 | Note length limit is unspecified ("reasonable maximum"). | UI assumes 120. | Pick the number; the UI follows. |
| B7 | Negative liquid balances and card credit (overpayment) are in the TLD edge cases. | UI shows "−₱…" and "Card credit …". | Confirm the API returns these as signed decimal strings. |

## 6. Tradeoffs considered

| Decision | Chosen | Alternative | Why / cost |
|---|---|---|---|
| Mobile navigation | Bottom bar with an **Add** item | Hamburger menu; floating action button | Three destinations fit a bar; thumb reach; a floating button would cover content. Cost: Add is the rightmost item, not centred. |
| Quick Add container | Bottom sheet on phones, centred dialog on desktop, one component | Full-page route; two components | No router, one focus trap, fewest steps. Cost: keyboard/viewport edge cases on iOS. |
| Add vs. edit | Same form | Separate forms | Less code; edit locks the type. |
| Money polarity | Income green with `+`, expense in **ink**, debt orange | Red expenses | Spending is normal; red is for errors. Cost: users used to red/green may look for red. Mitigated by signs, arrows and words. |
| Liability treatment | Own hue + word "owed" + limit track | One accent for all money | The prompt requires debt to be unmistakable; available credit must never read as cash. Cost: an extra hue. |
| Native selects/date | Native | shadcn `Select`, custom date picker | ADR-015; best phone UX; zero extra code. Cost: browser-dependent appearance. |
| Limit track | One tiny graphic per card | No graphic | The only graphic; shows room left at a glance without a chart library. Cost: a display-only ratio in the browser (C8). |
| Equation strip | Included | Omitted | Teaches the core idea to beginners and is the signature element. Cost: one more line. |
| Delete | Confirm, no undo | Soft-delete/undo | Simple, honest, matches the TLD (hard `DELETE`). |
| Pay-card preview ("after payment: …") | **Included as a labelled estimate, pending Q4** (revised after the Impeccable review) | Omit it | It prevents the double-count misunderstanding the app exists to avoid. Cost: display-only browser arithmetic in whole centavos; the saved result and the confirmation use server figures. |
| Activity totals when filtered | **Omitted** | Compute in the browser | Same reason (B5). |
